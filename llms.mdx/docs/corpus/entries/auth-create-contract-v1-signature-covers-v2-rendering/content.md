# A valid v1 create-contract authorization whose signature covers bytes it does not contain (/docs/corpus/entries/auth-create-contract-v1-signature-covers-v2-rendering)

Where it sits, inside `LedgerCloseMeta` (CAP-0046, CAP-0058):

- H-B16: a valid v1 create authorization: its signature covers the V2 rendering
- H-D5: HOST_FUNCTION_TYPE_CREATE_CONTRACT (v1) with address-credential auth
- H-F9: SorobanTransactionMetaExt v0 under the bare flag profile (no EMIT_SOROBAN_TRANSACTION_META_EXT_V1), v1 under base

## The shape

The same v1 create, its auth entry still carrying SOROBAN_AUTHORIZED_FUNCTION_TYPE_CREATE_CONTRACT_HOST_FN, but signed over the CREATE_CONTRACT_V2_HOST_FN rendering (empty constructor arguments) the host hashes: the contract is created. A verifier that recomputes the payload from the entry's bytes rejects a signature core accepted. Under the bare flag profile (no EMIT_SOROBAN_TRANSACTION_META_EXT_V1) the same call writes Soroban meta extension v0, without the fee breakdown base writes in v1. By design since protocol 22 (one valid payload per action; github.com/orgs/stellar/discussions/1501). tools/auth-payload-check.mjs re-checks the signatures with hand-encoded preimages.
