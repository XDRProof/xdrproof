# Map keys that collide (/docs/corpus/entries/scval-map-keys-collide-on-native-conversion)

Where it sits, inside `LedgerCloseMeta` (CAP-0046):

- H-B2: ContractDataEntry.val, ContractEvent.body.data, SorobanTransactionMeta.returnValue

## The shape

An ScMap may hold keys of different types that print the same: u32 1, i32 1, u64 1, the string "1" and the symbol "1" are five distinct, correctly ordered keys on chain. Converting the map to a native object keyed by text collapses them. js-stellar-sdk's scValToNative silently kept one of them (#1789). This entry is real stellar-core output: a contract wrote the map to storage, returned it and emitted it in an event.

The five keys are u32 1, i32 1, u64 1, the string "1" and the symbol 1. Each maps to a different value (10, 20, 30, 40, 50), so a conversion that drops entries is easy to detect.

## What a correct reader returns

This entry has an **SDK check** (1 of 263 entries do). It is a rule for the SDK's own helper, not a value: keep all five entries, or refuse the map. Never return fewer.

## What it reproduces

[js-stellar-sdk#1789](https://github.com/stellar/js-stellar-sdk/issues/1789)

`make conformance` runs a vector with the same kind of collision (a two-entry map whose keys both read as "1") through js-stellar-sdk builds before and after the fix. The [recorded matrix](/docs/tools/conformance) shows 17.2.0 and 17.2.1 keeping 1 of 2 entries, and 17.3.0 rejecting the map.
