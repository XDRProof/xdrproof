# Signed-payload signer (/docs/corpus/entries/signer-signed-payload-set-options)

Figure: the 44-byte signed-payload SignerKey from testnet ledger 4437357: type 3, a 32-byte ed25519 key, length 3, payload `de ad be`, and one byte of padding.

## The shape

CAP-0040 added a signer type that carries a payload: the strkey starts with P and is longer than a G address (up to 165 characters for a 64-byte payload). Readers that assume every signer is a 32-byte ed25519 key truncate it or fail. wallet-backend halted ingestion on testnet ledger 4437357 (#729) and stored the signer as 33 bytes, losing the payload (#716).

Where it sits, inside `LedgerCloseMeta` (CAP-0040):

- H-A3: SetOptionsOp.signer.key (SIGNER_KEY_TYPE_ED25519_SIGNED_PAYLOAD)

## Variants

One variant is **mined**: the real testnet ledger where wallet-backend halted. Two are **generated** by a standalone stellar-core v30.0.0, on the mainnet and testnet passphrases. The generated ones push the edges: a 64-byte payload (the longest allowed, a 165-character strkey), and a 29-byte payload that needs XDR padding.

## What it reproduces

[wallet-backend#729](https://github.com/stellar/wallet-backend/pull/729), [wallet-backend#716](https://github.com/stellar/wallet-backend/issues/716)

`make replay` feeds testnet ledgers 4437356–4437359 to three real wallet-backend builds through a mock stellar-rpc:

| wallet-backend build | Expected verdict |
|---|---|
| `79ea2acd`, "upgrade to protocol 28" (#715) | **stores the signer as 33 bytes**, losing the payload (#716) |
| `6e5a5910`, "reduce muxed addresses to their base account" (#693) | **halts** at ledger 4437357 |
| `2c873353`, "handle CAP-40 signed-payload signers" (#729) | **stores the full 41-byte key** |

The verdict is read from state: the ingest cursor and the stored signer's length. See [Replay](/docs/tools/replay).

## Check it yourself

```bash
make verify   # schema, hashes, byte-for-byte round trip, every fact above
make replay   # the wallet-backend runs (Docker, about 10 minutes cold)
```
